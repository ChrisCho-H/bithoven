1. Introduction

Bithoven is a high-level, imperative programming language designed for Bitcoin smart contracts. It bridges the gap between complex contract logic and the low-level stack machine of the Bitcoin Virtual Machine (VM).

Unlike writing raw Bitcoin Script—which is notoriously difficult and error-prone—Bithoven allows you to write readable, auditable code with modern control flow (if/else), named variables, and built-in safety checks. It compiles down to highly optimized native Bitcoin Script.

Why Bithoven?

  • Imperative Syntax: Use familiar control flow instead of mental stack juggling.
  • Formal Safety: A type checker, a liveness analyzer, a consensus-literal checker and a path-sensitive semantic analyzer reject anyone-can-spend paths, signature misuse, type errors and unspendable contracts before deployment.
  • Proven, then Tested: Type soundness and a refinement theorem connect the source to the emitted script, and the compiler is differentially tested against Bitcoin Core.
  • Low Overhead: On standard Miniscript policies, emitted scripts are within a median of one byte of rust-miniscript.

📊 Bithoven vs. Raw Bitcoin Script

❌ Bitcoin Script (Raw)
OP_IF
  <1000> OP_CSV OP_DROP

🆕 What's New in v0.1.0

v0.1.0 is a major revision of the analyzer and back end, accompanying the Bithoven paper.

  • Path-sensitive signature necessity. In 0.0.x, a declaration only had to contain a signature item, and only the literal shape !checksig(..) was flagged. v0.1.0 decides, for every path, whether it can succeed while every checksig fails. Rewrites that 0.0.x compiled into anyone-can-spend scripts, such as checksig(..) == false, checksig(..) || flag or an inverted if checksig(..), are now rejected. !!checksig(..), which 0.0.x wrongly rejected, now compiles. Details →
  • Dead-contract detection. A contract whose every path is provably unsatisfiable is rejected with DeadPath instead of compiling to an unspendable output.
  • Enforced well-formedness. Every if needs an else, there is exactly one stack declaration per spending path, and paths that split at a branch must agree on the witness items consumed before it.
  • Per-path liveness. Witness consumption is tracked per spending path, so two branches may reuse a name such as sig; 0.0.x rejected this with VariableConsumed.
  • Stricter types and literals. verify, return and if operands must be bool; byte strings are capped at the 520-byte push limit; key literals must use the target's encoding.
  • Back-end fixes. Equality over arithmetic compiles to OP_NUMEQUAL, so an overflowing sum can no longer compare equal byte-wise, and long byte-string literals that could crash the 0.0.x compiler now compile.
  • Reproducible evaluation. Differential validation against Bitcoin Core, mutation analysis, the BSHunter taxonomy benchmark and a false-positive corpus ship with the repository (see tests/README.md).

Upgrading from 0.0.x?

Contracts that relied on the looser rules may stop compiling. Give every if an else (NoReturn), write exactly one declaration per spending path (DeclarationPathMismatch), and use 32-byte x-only keys under taproot or 33-byte compressed keys under legacy/segwit (MalformedPubkey).

3. Structure of a Contract

A Bithoven contract (file extension .bithoven) consists of three main parts:

  1. Pragmas: Compiler directives.
  2. Stack Definitions: The expected input variables (Witness data), one declaration per spending path.
  3. Logic Block: The executable code, in which every path ends in a return.

Example: Single Signature

// 1. Pragmas
pragma bithoven version 0.0.1;
pragma bithoven target segwit;

// 2. Stack Input Definitions (The "Witness")
(sig_alice: signature)

// 3. Logic Block
{
    return checksig(sig_alice, "0245a6b3f8eeab8e88501a9a25391318dce9bf35e24c377ee82799543606bf5212");
}

4. Language Basics

Pragmas

Pragmas define the compiler version and the Bitcoin protocol target. The target controls opcode generation.

  • legacy: Generates P2SH-compatible script. Key literals are 33-byte compressed keys.
  • segwit: Generates P2WSH-compatible script. Key literals are 33-byte compressed keys.
  • taproot: Generates P2TR-compatible script (uses OP_CHECKSIGADD). Key literals are 32-byte x-only keys.

A key literal in the wrong encoding for the target, or one that is not a point on secp256k1, is rejected with MalformedPubkey.

Types

Type Description Example
bool Boolean values true
number Integer values (32-bit signed, ±2,147,483,647) 1000
string Hex or ASCII string data (at most 520 bytes) "secret"
signature ECDSA (legacy/segwit) or Schnorr (taproot) signatures, supplied by the witness sig_alice

Public keys are not a declarable type. A key must be a string literal such as "0245...", so a spender can never substitute a key of their own; a key taken from the witness is rejected with TypeMismatch.

Operators

Operands are type-checked at compile time; a mismatch is rejected with InvalidOperation.

Operators Operands Result
+ - max(a, b) min(a, b) ++ -- negate abs number number
< <= > >= number bool
== != Two operands of the same type: number, string or bool bool
&& || ! bool bool
sha256 ripemd160 number, string or bool (not signature) string
len string number
checksig signature and key literal pairs bool

Stack Input Definitions

Bithoven allows you to define multiple valid "spending paths" at the top of your file. The compiler verifies that every path is secure.

(condition: bool, sig_alice: signature) // Path A: the if side
(condition: bool, preimage: string, sig_bob: signature) // Path B: the else side

The compiler enforces four rules on declarations:

  • One declaration per path. A contract with k conditionals has k + 1 spending paths and needs exactly that many declarations, in the order the paths' returns appear in the source (the if side before the else side). Otherwise: DeclarationPathMismatch.
  • Consumption order. List items in the order the path consumes them. The first item is the top of the witness stack, so a branch condition comes first. Using an item while one listed before it is still unused is rejected with InvalidConsumptionOrder.
  • Shared prefix. Paths that split at a branch must declare the items consumed before it with the same names in the same positions (above, condition). Otherwise: DeclarationPathMismatch.
  • Exactly once. Every declared item is consumed exactly once on its path; UndefinedVariable, VariableConsumed and UnusedVariable catch the alternatives.

💡 A witness serializes the stack bottom-to-top, so when spending, the first declared item is the last one pushed.

5. Control Flow

Conditionals

Use standard if/else logic. Every if needs an else.

if condition {
    // Path A
    return checksig(sig_alice, "<pk_alice>");
} else {
    // Path B
    return checksig(sig_bob, "<pk_bob>");
}

Assertions

Halts execution if false.

// Fails transaction if false
verify sha256(preimage) == "53de...4e45f";

Structural Rules

Bithoven has no loops, recursion or calls, so a contract is a tree of if/else branches whose leaves are returns. The compiler requires that:

  • Every if has an else, and an if/else is the last statement of its block; put checks shared by both branches before it. (NoReturn, UnreachableCode)
  • Every path ends in return <bool>, and nothing follows a return. (NoReturn, UnreachableCode)
  • The operands of if, verify and return are bool. (InvalidOperation)
  • Every path requires a valid signature. A branch that can never succeed, such as else { return false; }, is fine as long as some path can. (NoSigRequired, UselessSig, DeadPath)

6. Bitcoin Primitives

Time Locks

The compiler range-checks every locktime literal and rejects one out of range with IntegerOverflow.

  • older <n> Relative Timelock (CSV). Input must be older than n blocks. 0 ≤ n ≤ 65,535, the 16 bits BIP-68 gives a relative locktime.
  • after <n> Absolute Timelock (CLTV). Block height must be greater than n. 0 ≤ n ≤ 4,294,967,295.

Cryptography

Hashing: sha256(data), ripemd160(data). Nested hashes compile to single opcodes: sha256(sha256(x)) becomes OP_HASH256 and ripemd160(sha256(x)) becomes OP_HASH160.

Length: len(s) returns the byte length of a string.

Signature Checks: Supports single and multisig via checksig. Keys must be literals in the target's encoding. Multisig compiles to OP_CHECKMULTISIG under legacy/segwit and to a chain of OP_CHECKSIGADD under taproot.

// Single Signature
checksig(sig_var, "pubkey_hex")

// 2-of-2 Multisig
checksig [2,
    (sig_alice, "pk_alice_hex"),
    (sig_bob, "pk_bob_hex")
]

7. Security Features

Bithoven is "Correct-by-Construction." A contract reaches the code generator only after passing all four analysis stages below, and every rejection comes with a diagnostic pointing at the offending line and column.

Analysis Pipeline

1. Type Checker

Rejects arithmetic on strings or on checksig results and comparisons across types. Keys must be on-curve literals in the target's encoding, so a spender cannot supply their own key (uncertain-sig) and no key is impossible to sign for (impossible-key).

2. Liveness & Scope Analyzer

Ensures every declared witness item (especially signatures) is consumed exactly once, in stack order, on every path, and that the declarations match the paths. Prevents signature reuse and leftover stack items.

3. Consensus-Literal Checker

Checks literals against Bitcoin's consensus limits: numbers fit the 32-bit script range, byte strings fit the 520-byte push limit, and locktimes fit their BIP-65 and BIP-68 fields.

4. Semantic & Control-Flow Analyzer

Enumerates every terminating path and asks whether it can succeed with every checksig forced to false, whether it can succeed at all, and whether it ends in an explicit return. Prevents anyone-can-spend bugs and unspendable outputs.

Signature Necessity

The central security property: no accepted spending path can succeed unless a checksig on that path returns true. Rather than matching syntactic patterns, the analyzer turns each path's success condition into a boolean formula, pins every signature check to false, and asks whether the formula can still be satisfied. Anything it cannot model exactly is treated as attacker-controlled, so it errs toward rejecting a contract, never toward accepting one.

This contract looks signature-gated, but its only path succeeds exactly when the signature check fails:

pragma bithoven version 0.0.1;
pragma bithoven target segwit;

(sig_alice: signature)
{
    return checksig(sig_alice, "0245a6b3f8eeab8e88501a9a25391318dce9bf35e24c377ee82799543606bf5212") == false;
}
Error at line 6:5: UselessSig("A checksig is present on the top-level path but it does not gate the spend: the return at line 6:5 can succeed without a valid signature.")

Because the check reasons about what each path computes rather than how it is spelled, equivalent rewrites get the same verdict (.. elides the signature and key):

Contract body Verdict
return !checksig(..); ❌ UselessSig
return checksig(..) == false; ❌ UselessSig
return checksig(..) || flag; ❌ UselessSig
if checksig(..) { return false; } else { return true; } ❌ UselessSig
if flag { return true; } else { return checksig(..); } ❌ NoSigRequired
verify false; return checksig(..); ❌ DeadPath
return checksig(..) == true; ✅ Compiles
return !!checksig(..); ✅ Compiles

The analysis is bounded at 20 attacker-controlled inputs per path; a path above the bound is rejected rather than trusted. Keyless spending paths, such as a bare hash lock or a bare timelock, are outside the guarantee by design and rejected with NoSigRequired.

Formal Guarantees & Evaluation

The Bithoven paper gives the language a formal syntax, big-step operational semantics and type system, and states two guarantees separately:

  • Safety (type soundness): an accepted program never reaches an undefined state of Bithoven's abstract machine (Progress and Preservation).
  • Security (refinement and signature necessity): if the emitted script succeeds on chain, the source program succeeds on a well-typed witness that agrees on every checksig outcome. Since no accepted path succeeds with every checksig false, some checksig must have returned true on chain.

The refinement theorem rests on an explicit trusted base, chiefly that Bitcoin Core implements the modeled fragment of Script. That assumption is tested rather than taken on faith:

Scope

Script-level resource limits (201 opcodes, 10,000-byte scripts, 1,000 stack items, 20 keys per multisig) are not enforced, so a very large contract can compile to an unspendable script. Taproot output is checked against expected opcodes but not executed against consensus, since libbitcoinconsensus has no taproot verification flag.

9. Frequently Asked Questions

Q: What is Bithoven?

A: Bithoven is a high-level, type-safe programming language for writing Bitcoin smart contracts. It provides imperative syntax (if/else, return) instead of low-level stack operations, and compiles to native Bitcoin Script.

Q: Do I need to know Bitcoin Script to use Bithoven?

A: No! That's the point. Bithoven abstracts away the complexity of Bitcoin Script's stack-based operations. You write readable code with familiar programming constructs, and the compiler handles the low-level details.

Q: How does Bithoven compare to Miniscript?

A: Miniscript (BIP-379) is a structured, composable subset of Bitcoin Script, best understood as an analyzable assembly language and compiler target. Its grammar has no named witness bindings, arithmetic or imperative control flow, so it obtains safety by excluding them. Bithoven is an imperative source language that admits those constructs and obtains comparable guarantees by analysis instead. On 17 standard Miniscript policies, its output is within a median of one byte of rust-miniscript's. A few Miniscript constructs have no Bithoven counterpart: pk_h, because keys must be literals; or_d, whose OP_IFDUP idiom conflicts with linear consumption; and thresh over arbitrary sub-policies, which Bithoven expresses only over keys (multisig) or as a conjunction.

Q: Why is my hash lock or timelock rejected with NoSigRequired?

A: By design, every spending path must require a valid signature. A bare hash lock lets anyone who sees the preimage, for example in the mempool, claim the coins, and a bare timelock lets anyone spend once it expires. Add a signature check to the path: verify sha256(preimage) == "<hash>"; return checksig(sig, "<pubkey>");

Q: My contract compiled with 0.0.x but fails with v0.1.0. Why?

A: v0.1.0 enforces rules that 0.0.x did not. The most common fixes are giving every if an else, writing exactly one stack declaration per spending path, and using the key encoding the target requires. See What's New in v0.1.0 for the full list.

Q: What's the difference between older and after?

A: older N is a relative timelock (OP_CHECKSEQUENCEVERIFY) - locks coins for N blocks after the UTXO is created. after N is an absolute timelock (OP_CHECKLOCKTIMEVERIFY) - locks coins until block height N. Use older for "wait X blocks from now", and after for "unlock at specific time".

Q: Can Bithoven create multiple outputs or check UTXO values?

A: No. Bitcoin Script (and therefore Bithoven) has amount blindness - scripts cannot read UTXO values or control output amounts. These require pre-signed transactions or off-chain coordination. Bithoven focuses on spending conditions, not transaction construction.

Q: Is Bithoven production-ready?

A: Bithoven v0.1.0 is in beta. The paper proves type safety and refinement for the language, and the compiler is differentially tested against Bitcoin Core, but it has not been independently audited. It also does not enforce Bitcoin's script-level resource limits, and its taproot output has not been executed against consensus (see Scope). Use it for research, prototyping, and learning. For production deployments, test on regtest or signet and conduct a security review.

Q: How do I test my Bithoven contracts?

A: Use the Web IDE for quick experimentation. For thorough testing, compile your contract and use Bitcoin testing frameworks like bitcoin-core regtest or btcd.

Q: Where can I get help?

A: Check the GitHub repository for documentation, or open an issue if you encounter problems. For research questions, refer to the Bithoven paper.

10. Glossary

Bitcoin Script
A stack-based programming language used to define spending conditions for Bitcoin transactions.
UTXO
Unspent Transaction Output - a chunk of bitcoin that can be spent by satisfying its script conditions.
Witness
The data provided to satisfy a script's spending conditions (signatures, preimages, etc.).
SegWit
Segregated Witness - a Bitcoin upgrade separating witness data from transaction data for efficiency.
Taproot
Bitcoin's 2021 upgrade enabling more efficient and private smart contracts via Schnorr signatures and MAST.
HTLC
Hash Time-Locked Contract - combines hash locks and timelocks for conditional payments (used in Lightning).
Multisig
Multi-signature - requires multiple signatures to spend (e.g., 2-of-3 means any 2 of 3 parties can spend).
CLTV / CSV
CheckLockTimeVerify (absolute) / CheckSequenceVerify (relative) - opcodes for timelocks.
Atomic Swap
Trustless cross-chain exchange using matching hash locks on different blockchains.
Opcode
Operation code - a single instruction in Bitcoin Script (e.g., OP_CHECKSIG, OP_IF).
Preimage
The secret data that, when hashed, produces a specific hash digest used in hash locks.
Spending Path
A distinct execution branch in a contract with its own witness requirements.
Stack Declaration
The typed list of witness items one spending path consumes, written top of stack first.
Signature Necessity
Bithoven's core security property: no spending path can succeed unless a signature check on it returns true.
